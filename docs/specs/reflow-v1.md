# [Spec] 回流 v1：校准定位 · 看得见的监控 · 证据质量门禁

> 状态：ready-for-agent。拍板记录：签字凭证 = 台账（ADR-0003）；出厂样例 = 假样例盖标签（ADR-0004）；口径一改即不可比（只记录、不判好坏）；唯一事实源 = GitHub。

## Problem Statement（问题）

一个人用了很多 AI 聊天工具，散落在几十个聊天窗口里的“我是谁、我怎么取舍、我踩过什么坑”没有被收起来。每次换一个 AI，他都要从头解释一遍；AI 还总把他粘贴的提示词、别人的材料当成“他说的”。

仓库里已经有一套能把聊天记录变成 6 份档案的工具，但三个问题让它没有真正交付：

1. **定位被说歪了。** 文档和对话里把它说成“某个人的判断合集”，它本该是“让任何用户提取自己判断的工具”。定位歪了，用户故事和验收标准都跟着歪。
2. **改了什么说不清。** 脚本一改，没人能回答“这一步进去什么、出来多了什么、指标变了没”。实测：真实档案缺写入标记，候选一条都写不进去（applied=0）；补一行标记后写进去 6 条（applied=6），但打分卡一分没涨——这种“变了 / 没变”必须每一步都看得见。
3. **证据没有门禁。** L2 把“来源文件命中数”当成“跨对话复现”，把用户粘贴的提示词模板当成原话。L3 审计发现一条号称 6 个来源的候选，实际只有 1 条是本人对题说的；而被打回的候选，写回程序照样把它写进档案。

## Solution（方案）

- **定位**：所有对外文案统一为“工具 + 用户自己的判断”；芯火只是第一个用户。
- **监控**：每一步把进去什么、出来什么、变了多少、退出码、耗时写进一本台账；改脚本必须附改前改后两行。
- **证据**：每条证据标三类之一——本人对题 / 模板或外部材料 / 跑题；“来源数”只数本人对题的；L3 只归纳通过审计的，被打回的不许写回。

做完之后，用户跑一条命令，就能看到：这一轮多了几条判断、哪几条要他签、6 份哪里变厚了、哪项指标还没达标。

## User Stories（用户故事）

**作为用户（操作者）**

1. 用一句命令跑完整个流程，不用记一串脚本。
2. 跑完看到“这轮多了几条判断、哪几条要我签”。
3. 每条候选都带我当时的原话和出处，我能判断它是不是我的意思。
4. 不是我说的（粘贴的模板、别人的材料、AI 的转述）被标出来，不会混进我的档案。
5. 逐条签字，不是一键全同意。
6. 看到“改前 vs 改后”的对比，知道这次改动有没有用。
7. 新对话进来还能再跑一遍，档案跟着我长。
8. 任何 AI 读这 6 份就能按我签过的判断做事，不用我每次重新解释。
9. 工具出厂不带别人的判断，我不会被别人预置好的判断带偏。
10. 有一份明确标注“样例、非本人”的演示档案，我知道成品长什么样。
11. 哪一步卡住了（缺写入标记、校验失败、主线不唯一）能直接看到，不用猜。
12. 02 里至少有几条带出处的判断，不是空壳。
13. 主线只有一条。
14. 每条观察能看到“有几条证据、来自几场对话”，判断它稳不稳。
15. 被打回的候选写明原因和下一步（补访谈 / 放弃），并且不会出现在档案里。
16. 我签过的每一条都有台账可查：谁、几点、哪条、内容指纹。

**作为接手 Agent（只读 6 份的那个 AI）**

17. 读 AGENTS + 00 就知道去哪找判断、规则、案例。
18. 候选和定稿在视觉上分开，不会把待确认当事实。

**作为开发者 / 审计者**

19. 每步台账是机器能读的，能画趋势、做回归。
20. 校验门禁在 CI 里跑，不合格的改动进不了主线。
21. 签字和样例的决策写成 ADR，以后改的时候知道当初为什么。
22. 每条判断能看到反例或“未检索到反例”，不是只找支持证据。

## Implementation Decisions（实现决策）

**定位与文案**

- 所有对外文案（README、AGENT_START_HERE、6 份模板、提示词）统一为“工具，产出是用户自己的判断”；删除这类把人当作产品内容的说法。
- `GLOSSARY.md` 已补齐并改用统一格式：用户、本人、接手 Agent、原话、证据、候选、判断、签字、待确认区、6 份、写入标记、主线、回流、回填、applied、台账、口径版本、打分卡、盲测、ADR。
- “判断”采用三种形态：准则（02）、规则（03）、案例（04）。L3 观察可以落在任一形态。
- 修掉模板与实物的名字漂移：模板与真实档案统一为 `04-正反例避坑账.md`（旧名作为代码兼容别名保留）。

**监控与台账**

- 新增一个管线审计模块，按步骤追加写 `io_ledger.jsonl`。每行固定列：`run_id / step / 口径版本 / input_count / output_count / new_count / actor / exit_code / seconds / timestamp / note`。
- 候选级字段：`evidence_count`（证据条数）、`personal_on_topic_count`（本人对题条数）、`conversation_count`（来源对话数）。
- 台账是监控的唯一事实源。打分卡四项与 `applied / candidates` 作为字段写进同一台账，不另开报告。
- 入口统一为一个 CLI 子命令；`apply` 并入同一入口；`audit` 作为子命令。
- **改进门禁**：任何改脚本的工单，交付必须附“改前 / 改后”两行台账；没变化的字段明写“无变化”。
- **口径版本**：口径一改就升版本并标记“跨版本不可比”，历史行只记录、不参与好坏判定。

**写回与写入标记**

- 初始化和构建流程对已存在的 6 份做幂等补标记：末尾没有写入标记就加一行；已有则不动。
- 真实档案补完标记后，候选应能进待确认区（applied 从 0 到 6），正文不变。
- 被打回的候选不得写回：写回只接受 `status = approved_for_pending` 的候选。

**证据审计**

- 每条 L2 候选的每一条证据标三类之一：`personal_on_topic / prompt_or_external / off_topic`，逐条带记录编号。
- 候选的“来源数”改为“本人对题的来源对话数”；来源文件命中数另存 `source_file_hits`，不再混用。
- L3 只归纳本人对题证据 ≥ 1 的候选；一条观察要求 ≥ 2 条本人对题证据，保留反例栏（没有就写“未检索到”）。
- 被打回的候选进 `rejected` 台账，带原因和下一步（补访谈 / 放弃）。

**签字**

- 签字走台账（ADR-0003）：`reviewer / signed_at / candidate_id / content_fingerprint`。不加密；防篡改列为后期。

**内容质量**

- 02 至少 3 条带原文出处的判断句，让打分卡的“判断准则”槽位被覆盖。
- 主线候选收敛到 1 条，其余进历史区。
- 盲测：接手 Agent 只读 6 份 + 检索，答一组判断题，输出正确率；题目和答案只来自签过字的条目。

**出厂样例**

- 带一套编造的演示档案，每份首页盖“样例·非本人”，程序默认不加载为用户档案（ADR-0004）。

## Testing Decisions（测试决策）

- **好测试的标准**：只测外部行为——命令退出码、台账里的行、6 份文件的字节变化。不测脚本内部函数。
- **唯一接缝**：一条命令进，台账和文件字节出。不新开第二个接缝。
- **要测的模块**：CLI 入口、管线审计模块、补标记、L2 候选构建（证据三分类）、L3 观察、02 / 主线校验、盲测。
- **先例**：`tests/test_pipeline.py` 的“临时 db + 断言报告字符串”风格；`99_smoke.py` 的端到端冒烟；`blind_test.py` 的答题框架。
- **必测场景**：
  1. 真实档案没标记 → 写回安全失败、台账记 `applied=0`。
  2. 补标记 → 写回 6 条、正文不变、台账记 `applied=6`、字节增量 > 0。
  3. 候选含提示词模板 → 证据标 `prompt_or_external`，“来源数”不计。
  4. 候选只有 1 条本人对题 → L3 不归纳。
  5. 被打回的候选 → 不出现在 6 份里。
  6. 02 没有带出处判断 → 打分卡覆盖度缺“判断准则”，FAIL。
  7. 主线 3 条 → 主线唯一 = 0，FAIL；收敛到 1 条后 PASS。
  8. 盲测题目全部来自签字条目；未签字条目不得出题。
  9. 重复跑补标记 → 文件不变。
  10. 同一脚本连跑两次 → 台账新增两行，`口径版本` 一致，可比。
